# Feature Specification: Adoção Local de Ferramentas ArtCraft para Autoria de Ativos

**Feature Directory**: `specs/003-artcraft-local-authoring`

**Created**: 2026-10-17

**Status**: Draft

**Input**: Assessment handoff from `.specify/assessments/artcraft-horror-comic-reform` (verdict: go): adotar a suíte ArtCraft como ferramentas de autoria **locais** (Option B) para produzir masters em `media-src/`, mantendo o pipeline de build, o player, o schema do manifesto e os orçamentos inalterados.

## Clarifications

> Nota: as clarificações abaixo estão organizadas por sessão/lote para rastreabilidade. As decisões normativas consolidadas estão em FR-001…FR-014 e SC-001…SC-007b; em caso de conflito, prevalecem os FR/SC.

### Session 2026-10-17 (assessment handoff)

- Q: Qual é o escopo da reformulação? → **A: Apenas autoria/regeneração de ativos (`media-src/` → `assets/` via pipeline existente).** Runtime, player, schema do manifesto e orçamentos permanecem inalterados (Princípio II e IV da constituição).
- Q: Quais apps da suíte serão usados? → **A: Subconjunto mínimo `vectorcraft` (ilustração/vetor) + `photocraft` (tratamento de imagem)**, com `designcraft` opcional para artes promocionais fora do runtime. Licença MIT (dual MIT/Apache-2.0).
- Q: A adoção é integrada ao CI? → **A: Não.** Autoria local-only; nenhum binário ArtCraft entra no repositório ou no CI. A Option C (integração completa) fica para avaliação futura.
- Q: Formatos de exportação? → **A: SVG/PNG (vectorcraft/photocraft) → re-codificação pelo pipeline existente (sharp) para AVIF/WebP/JPEG + srcset.** Integração SVG→sharp validada localmente.

### Resolved clarifications (Session 2026-10-17)

- Q: Scope of metadata → **A (custom)**: update image assets, `alt`, `description`, and narrative metadata/durations **as appropriate** (where it improves the comic), keeping pacing validated by perf tests. No blanket rewrite of timing. Refined by the research-backed clarification "Metadata update rule" (F20 staleness trigger, >10% duration recompute threshold, pass criteria).
- Q: Minimal app subset → **A (custom)**: use **all valid** ArtCraft apps that produce masters within the accepted formats and constraints (vectorcraft, photocraft, designcraft, and others as justified), not only the initially proposed subset. Runtime-impacting apps (filmcraft, effectcraft) remain out of scope for the runtime.
- Q: Subjective quality → **A + B**: stakeholder visual review **plus** a side-by-side comparison with documented notes (size, format, qualitative impression) for each integrated master.

### Resolved clarifications (Session 2026-10-17, batch 2)

- Q: App validity criteria → **A**: validity is **format-and-constraint-based** (accepted format SVG/PNG/JPG/WAV within existing limits: ≤2560 px, ≤300 KB/quadro, ≤30 MB total, AAC/Opus audio; compatible license MIT option; no runtime/CI dependency). No app allowlist; video/motion apps excluded by output type.
- Q: Traceability mechanism → **A**: **commit-message trailers** (e.g. `Authored-With: vectorcraft-cli 0.12.0`) as primary, with an **optional JSON sidecar in `media-src/`** (never in `assets/`) for richer provenance. Manifest fields rejected (frozen v1 schema).
- Q: Failure handling for invalid masters → **A**: **fail-fast** in `build`/`build:images` (throw on invalid master, missing light variant, budget overrun, unsafe ref); no skip flags. Reporting tools (`compatibility-report.mjs`; the internal permissive mode `validateManifestIntegrity(..., { checkFiles: false })` — there is no CLI flag) may remain permissive.

### Resolved clarifications (Session 2026-10-17, research-backed)

- Q: Audio authoring scope → **A (research-backed)**: audio masters remain **WAV from any stable DAW**; authoring is tool-agnostic. ArtCraft `soundcraft` is **pre-alpha** (incomplete buffer selection/MIDI/interchange) and is **not** a production dependency for this feature; it may be reconsidered once stable. Audio pipeline (ffmpeg → AAC/Opus) and bitrates remain unchanged (FR-003/FR-009). Loudness normalization and WCAG 1.2.1 transcripts are recommended enhancements but are deferred to planning to respect the "output contract unchanged" constraint.
- Q: SVG content security → **A (research-backed)**: SVG masters must pass a **build-time sanitization/validation gate** (reject `<script>`, on* handlers, `foreignObject`, external `href`/`xlink:href`, DOCTYPE/entities) with **fail-fast** on violation, in addition to the existing safe-local-reference and external-origin checks. Masters are rasterized by sharp and never published as SVG. Browser image-sandboxing is defense-in-depth only; no CSP/runtime change is introduced (scope constraint). Sanitizer choice (e.g. DOMPurify/svg-sanitizer/librsvg hardening) is a planning detail.
- Q: Provenance enforcement level → **A (research-backed)**: **split enforcement** — (1) **sidecar digest** is verified in `build`/`build:images` when present (fail-fast on mismatch/invalid JSON; no-op when absent), validating SHA-256 of the master bytes against the sidecar; (2) **commit trailers** are verified **only** by a new step in `.github/workflows/ci.yml` with `fetch-depth: 0`, **forward-only** (commits touching `media-src/` from this feature's merge onward; pre-existing commits are grandfathered), **never** in `npm run ci` nor in the core build (which must work in shallow/tarball/offline contexts). Manifest fields remain prohibited (schema v1 frozen). This is a provenance-inspired authoring sidecar with build-time digest verification (the metadata is human-authored, not build-generated) and follows C2PA's sidecar storage ordering (non-embeddable cases); it is not SLSA-conformant, because SLSA covers builds, not local authoring; C2PA 2.4 defines `humanOversightLevel` only for AI-generated content (§18.28, see batch 6 correction), so no C2PA oversight field applies to these human-authored masters.
- Q: Visual quality gate → **A (research-backed)**: two-tier gate — **Tier A** (human): stakeholder visual review + documented side-by-side notes (size, format, qualitative impression) per master, recorded via commit trailer and optional sidecar (unchanged). **Tier B** (automated, CI): delivery-fidelity check comparing each generated variant to a lossless PNG reference of the master at each delivery width using **SSIM ≥ 0.95** (standard) / **≥ 0.90** (light, intentional degradation accepted) and **PSNR ≥ 30 dB** floor, computed with ffmpeg's built-in `ssim` filter (no new dependency; ffmpeg already required by preflight); fail-fast for standard variants, warn-only for light. **Tier D**: synthetic fixtures get no perceptual gate (structural/byte/integrity only). Tier C (SSIMULACRA 2/LPIPS) is an offline maintainer aid, not a CI gate.
- Q: Metadata update rule → **A (research-backed)**: replace the vague "as appropriate" with concrete triggers — (1) **F20 staleness rule**: update `alt` and `description` in the **same change** that modifies a frame's image or narrative beat; (2) recompute `durationMs` only when the minimum dwell changes by **>10%** or crosses the 500 ms floor; (3) pass criteria: `alt ≠ description`, `alt ≤ 125 chars`, `description` reproduces all visible lettering, `durationMs ≥ minMs` where `minMs = 500 + (words/150)·60000 + 1000` (clamped to [500, 30000]) — `words` = número de palavras do `description` do frame (fórmula equivalente: `1500 + 400·words` ms). No blanket rewrite of timing; the perf SC-018 transition durations (120 ms fixture / 700 ms production) remain authoritative — SC-018 is a **pre-existing/external performance criterion, not defined by this feature**.

### Resolved clarifications (Session 2026-10-17, research-backed, batch 2)

- Q: SVG sanitization reject list → **A (research-backed)**: the enumerated set in FR-002 is a **minimum baseline, not an exhaustive list**. The gate must also reject (at least): CSS vectors (`url()`, `@import`, `image-set()`, `expression()`, `-moz-binding`, `behavior:` in `style`/`<style>`; prefer rejecting the `<style>` element and `style` attribute entirely for authored masters), all `data:` URIs in any URL-valued attribute, SMIL animation elements/attributes that mutate `href`/`xlink:href` (`animate`, `set`, `animateMotion`, `animateTransform`, `discard`), dangerous elements DOMPurify forbids (`iframe`, `object`, `embed`, `base`, `meta`, `link`, `form`, `template`, `noscript`, `style`, `handler`, `listener`), `xml:base`, `externalResourcesRequired`, processing instructions, XInclude, and **all DOCTYPE** (not just entities) for XXE/billion-laughs hardening, plus file-size/element-count/nesting-depth DoS caps. **Hybrid posture recommended**: reject list as floor **plus** an allow-list over the minimal SVG vocabulary vectorcraft emits (fail-closed); allow-list vocabulary finalization is a planning detail. Masters are never published as SVG and are rasterized by sharp/librsvg, so the gate also protects the build host (SSRF via external refs, XXE/DoS via libxml2), not just browsers. Sanitizer runs **before** `sourceWidth()`/`encodeImage()` (`build-images.mjs:68-98`); sharp `failOn: 'error'` + `limitInputPixels` remain backstops. Internal `url(#…)` refs must remain allowed.
- Q: Promotional art location & handling → **A (research-backed)**: promotional art (designcraft) lives in a **top-level `marketing/` directory** (localização autoritativa; `docs/marketing/` fica fora de escopo), **outside** both `assets/` (publishable runtime tree) and `media-src/frames|audio` (master input roots), so `build:images`/`build`/`validate` never pick it up and it is neither manifest-referenced nor counted in `budget.json`. It is authored/exported already-optimized (final delivery dimensions) and is **not** routed through sharp/esbuild; no AVIF/WebP/JPEG srcset or `-light-*` variant. Provenance via commit trailer (`Authored-With: designcraft-cli <version>`) + optional sidecar digest in `marketing/` (never `assets/`), per FR-008. Licensing: adopt ArtCraft's MIT option (preserve copyright/license notice); never redistribute ArtCraft marks (nominative use only); verify bundled-asset licenses (`ASSETS.md`) before publishing. If an OG/social image must ship in `dist/`, add an explicit, documented copy step in `build.mjs` (not via `assets/`); otherwise out of scope.
- Q: ArtCraft version policy → **A (research-backed)**: **two-tier, docs-only** — (1) **no minimum/recommended version is enforced in CI or preflight** (ArtCraft is local-only; enforcing would couple CI to an uninstalled binary and violate FR-004/SC-005); (2) document a **"tested-with" version** (seeded from the validated inventory, e.g. `vectorcraft 0.12.0`) in `docs/authoring.md` as advisory, updated when a newer version is validated. Drift is handled by **recording, not blocking**: trailer/CI script validates trailer *syntax* and *presence* on commits touching `media-src/`, but accepts any newer version; when both trailer and sidecar are present they must agree. Reproducibility is protected by the sidecar digest (bytes) + Tier B delivery-fidelity (SSIM/PSNR), not by pinning the authoring tool (SLSA does not cover local authoring steps; at most SLSA Build L1-analogous ("documented process")). Exact pinning is reserved for byte-reproducible media outputs (mp4-fixtures-style pinned binary + SHA) only if needed.

### Resolved clarifications (Session 2026-10-17, research-backed, batch 3)

- Q: Sidecar naming convention → **A (user)**: **extension-swap** — sidecar path = master path with extension replaced by `.json` (e.g. `media-src/frames/frame-01.svg` → `media-src/frames/frame-01.json`). Stem matches master stem exactly (simplest lookup and `discoverSources` exclusion); aligns with "same basename" literally; format-agnostic (one sidecar per master regardless of svg/png/jpg). **Sidecar schema (research-backed)**: `schemaVersion` (string, required), `subject: { name (master basename), digest: { sha256: "<64-hex-lowercase>" } }` (required), `provenance: { tool, toolVersion, timestamp (ISO-8601 UTC), author }` (required), optional `inputs: [{ uri, digest: { sha256 } }]`. Validation (fail-fast): parse must succeed (throw on invalid JSON); required fields present with correct types; `sha256` is 64 lowercase hex; timestamp parses as ISO-8601 UTC; recompute SHA-256 of master bytes and compare to `subject.digest.sha256` (mismatch → throw; direct comparison — constant-time not required, per the batch-5 correction); `subject.name` must match the master basename (stale → throw); **reject unknown fields** (strict) to catch drift. No-op when sidecar absent. Sidecar lives only in `media-src/` (never `src/`/`assets/`); placement enforced regardless of naming (a bare `.json` under `src/data/` would otherwise be published by `copyPublishableFiles`).

### Resolved clarifications (Session 2026-10-17, research-backed, batch 4)

- Q: Audio transcripts / WCAG 1.2.1 → **A (research-backed)**: ambient/background music and non-informational sound effects do **not** require a transcript under WCAG 1.2.1; the criterion targets *information* conveyed by audio. Compliance is satisfied by (1) a short text alternative per WCAG 1.1.1 (the frame `description`/`alt`, already required) identifying the audio (e.g. "decorative ambient music"), and (2) WCAG 1.4.2 audio control (pause/mute/independent volume) for any autoplay >3 s, which the existing `AudioManager` provides. An audio track that carries *essential narrative information* (e.g. a spoken cue or a sound signaling a plot event) MUST have that information captured in the frame's `description` (or a documented transcript) under 1.2.1. No new manifest field, schema change, or caption region is introduced; schema v1 stays frozen. (Research: W3C Understanding SC 1.2.1; Technique G158 — mentions dialogue/sounds, not music; W3C AGWG issue #4398, Mike Gower: "no need to do anything for background music … equivalent can be provided with the 1.1.1 requirement"; EN 301 549 §9.1.2.1 / Section 508 incorporate WCAG verbatim.)
- Q: Audio loudness normalization → **A (research-backed)**: **deferred to planning as a documented authoring target, not a build gate.** Adopted target for authored masters: **−14 to −16 LUFS integrated, true peak ≤ −1 dBTP**, normalized with ffmpeg `loudnorm` (two-pass) at authoring time (EBU R128/ITU-R BS.1770 broadcast −23 LUFS is inappropriate for web; streaming norms are −14/−16). The build pipeline does **not** add a hard LUFS gate (brittle on short clips); it MAY measure and report (warn) and hard-fails only on true-peak exceedance/clipping. Per-frame/per-scene perceived levels continue to be balanced via manifest `volume` (0–1) + global gain. Pipeline, bitrates and schema remain unchanged (FR-003/FR-009). Target documented in `docs/authoring.md` (to be created). (Research: EBU R 128/ITU-R BS.1770; Spotify −14 dB LUFS; Apple Music −16 LUFS; ffmpeg `loudnorm` filter docs; WCAG 1.4.2.)
- Q: Stale generated variant cleanup → **A (research-backed)**: **no generator-side auto-cleaning.** `build:images` keeps its incremental `isFresh`/`ensureImage`/`ensureAudio` skips and the existing validation gate `findUnreferencedAssets === []` (which fails the build on stray outputs) stays in force; `copyPublishableFiles` already excludes unreferenced files from `dist/`. If explicit cleanup is ever wanted, it must be a separate, documented step (e.g. `npm run clean:assets`), not part of `build:images`, so manifest drift surfaces as a hard error rather than being silently erased. This preserves the "output contract unchanged" constraint (FR-003) and reproducibility. (Research: Vite `emptyOutDir`/manifest-diff patterns; MSBuild incremental; Unity clean-build guidance; project's own `findUnreferencedAssets` invariant.)
- Q: Tier A visual review notes & sign-off → **A (research-backed)**: extend the `ProvenanceSidecar` with an **optional** `review` object (`reviewer` string required within block, `reviewedAt` ISO-8601 UTC, `oversight` ∈ {`human_authored`, `human_assisted`, `human_reviewed`} (changed from C2PA-reused values per Q3), `notes` string (side-by-side: size/format/qualitative impression), `decision` ∈ {`approve`, `reject`}, optional `measuredSSIM` number) and add a `Reviewed-By: <name>` commit trailer. Strict sidecar validation is extended to validate the block when present (absent allowed); Tier A gate requires the review block + `Reviewed-By` trailer for any master-integration commit. Self-review by the maintainer is acceptable (solo maintainer); a second reviewer is encouraged but not mandatory. The `oversight` vocabulary is **project-defined for human-authored masters** (`human_authored`/`human_assisted`/`human_reviewed`), not the C2PA `humanOversightLevel` values (which apply only to AI-generated content); no SLSA/in-toto ceremony is introduced. (Research: git-native sidecar + trailer pattern; C2PA v2.4 human oversight levels; ITU-T P.800.2 non-comparability of subjective MOS; project's `docs/image-quality-assessment.md` author+maintainer second pair of eyes.)

### Resolved clarifications (Session 2026-10-17, research-backed, batch 5)

- Q: Qual o canvas de exportação de um master autoral e o que fazer quando a arte não cabe no orçamento por frame? → **A (research-backed)**: canvas de autoria **1200×800 px (3:2)** — a geometria declarada no manifesto e a maior largura entregue; masters com lado maior >1200 px são rejeitados pelo build (fail-fast, `invalid-master-geometry`); o limite de 2560 px do FR-002 permanece como teto do pipeline, não como alvo. O orçamento por frame é a **soma do maior AVIF + maior WebP + maior JPEG (+ áudio do frame)** ≤ 300 000 B, com variantes light excluídas do valor por frame; baseline atual medido: 44 768 B no frame mais pesado (frame-03), folga ≈ 255 232 B (~249 KiB). `build-images.mjs` ganha **piso de qualidade explícito** (standard: AVIF ≥30 / WebP ≥45 / JPEG ≥45; light: AVIF ≥20 / WebP ≥30 / JPEG ≥30) e **throw nomeando o frame** em vez de degradar silenciosamente. Evidência: `budgetReferencesForFrame` (build.mjs:515-525) soma o maior candidato por formato; arte detalhada simulada = ~952 KB a 1200 px e ~4,3 MB a 2560 px; sharp `withoutEnlargement`/web.dev.
- Q: Qual métrica e qual imagem de referência o portão Tier B deve usar? → **A (research-backed)**: ffmpeg **não tem filtro `ms_ssim`**; usa-se `ssim` + `psnr` nativos (sem libvmaf, sem nova dependência). Referência = **PNG lossless do master em cada largura de entrega**, comparada por largura (nunca contra o master em tamanho nativo). SSIM ≥ 0,95 (standard) / ≥ 0,90 (light); PSNR ≥ 30 dB como piso de falha catastrófica. **fail-fast para variantes standard, warn-only para `-light-*`**; quando o orçamento de bytes vincular, reportar SSIM/PSNR alcançados por frame. Tier D (fixtures) sem portão perceptual; Tier C (SSIMULACRA 2/LPIPS) segue como auxílio offline.
- Q: Onde os portões de sanitização SVG, digest do sidecar e fidelidade Tier B devem executar? → **A (research-backed)**: os três dentro de `scripts/build-images.mjs` (único módulo com masters e variantes): sanitização antes de `sourceWidth()`/`encodeImage()`, digest por master, Tier B após `ensureImage()`. A verificação de **trailers de commit roda apenas em novo step de `.github/workflows/ci.yml`**, com `fetch-depth: 0`, **nunca em `npm run ci`** (preserva offline/tarball). FR-003 passa a significar "contrato de saída inalterado" (formatos, srcsets, `-light-*`, `budget.json`), não "scripts inalterados". Sidecar só é honrado em `media-src/` (`.json` em `src/` seria publicado; em `assets/` falha `findUnreferencedAssets`).
- Q: Sobre qual intervalo de git os trailers devem ser exigidos? → **A (research-backed)**: **forward-only** (commits que tocam `media-src/` a partir do merge da feature); commit(s) preexistentes **grandfathered** (o único commit que toca `media-src/` é um squash sem trailers; shallow clone/rebase-merge destroem trailers). Digest do sidecar: **fail-fast em mismatch, no-op quando ausente** (registrar, não bloquear); comparação constant-time não é exigida. Correção factual (revisada): o C2PA 2.4 **define** `humanOversightLevel` (`fully_autonomous`/`prompt_guided`/`human_validated`) na asserção `c2pa.ai-disclosure` (§18.28), mas apenas para conteúdo gerado por IA; o vocabulário `oversight` é **project-defined para masters autorais**; a reutilização dos valores do enum C2PA foi **substituída** por valores project-specific (`human_authored`/`human_assisted`/`human_reviewed`) per Q3. O alinhamento é **"SLSA Build L1-analogous"**, pois SLSA cobre builds, não autoria local.
- Q: Quantos frames devem ser autorados para a feature estar concluída? → **A (research-backed)**: **todos os 4 frames** nesta feature; o estado misto sintético+autoral **não deve ser publicado**. SC-001 era o mínimo, não o alvo; o Princípio V da constituição exige arte "coerente em estilo, resolução e paleta". Adiciona-se verificação documentada de **paleta/tonalidade** às notas Tier A (revisão humana, não novo portão automatizado).

### Resolved clarifications (Session 2026-10-17, research-backed, batch 6)

- Q: Como recuperar de um build interrompido (variante parcial/corrompida)? → **A (research-backed)**: **escrita atômica** — `encodeImage`/`encodeAudio` e o rasterizador de referência do Tier B escrevem primeiro num arquivo temporário no **mesmo diretório** do destino e só então fazem `rename()` sobre o alvo (write-temp → rename). Uma interrupção nunca deixa variante parcial visível, então reexecutar `build:images` é sempre seguro; o throw de `ensureImage` para output inválido (`"failed validation and must not be overwritten"`) permanece apenas como **rede de segurança**, não como caminho de recuperação esperado. Não altera o contrato de saída (FR-003) nem a política de "sem auto-limpeza". (Research: write-temp→fsync→rename é o padrão consolidado para escrita atômica — LWN "A way to do atomic writes"; Prometheus "Atomic Writes and the Textfile Collector"; Rust `tempfile::persist`; a alternativa "sobrescrever direto" é justamente a que produz arquivos truncados.)
- Q: O vocabulário `oversight` é definido pelo C2PA ou pelo projeto? → **A (research-backed, correção factual)**: o **C2PA 2.4 define** níveis de supervisão humana — campo `humanOversightLevel` com enum `{fully_autonomous, prompt_guided, human_validated}` na asserção `c2pa.ai-disclosure` (§18.28) —, mas **apenas para conteúdo gerado por IA**; o C2PA não define um campo de revisão humana para conteúdo autoral (não-IA). Portanto o bloco `review.oversight` permanece **project-defined para masters autorais**. A reutilização dos valores C2PA foi **substituída** por valores project-specific (`human_authored`/`human_assisted`/`human_reviewed`) per Q3 (mudança de schema). A afirmação anterior de que "C2PA não define níveis de supervisão humana" é **incorreta** e fica corrigida. (Research: C2PA Specification 2.4 §18.28 `c2pa.ai-disclosure` / `human-oversight-enum`.)
- Q: Como impor o bloco `review` do Tier A para commits de integração de master, se o sidecar é "opcional" e o build é no-op quando ausente? → **A (research-backed)**: **fail-closed no passo de CI** — para todo commit que toca `media-src/`, o novo passo em `.github/workflows/ci.yml` (com `fetch-depth: 0`) exige (1) um sidecar para o master com bloco `review` presente e `decision: approve`, e (2) os trailers `Authored-With` e `Reviewed-By`; ausência de qualquer um → falha. O build (`build:images`) permanece **no-op quando o sidecar está ausente** (a verificação de digest é só de integridade), preservando o contrato offline/tarball; a imposição vive **apenas** no CI. Efeito: o sidecar passa a ser **efetivamente obrigatório para commits que tocam `media-src/`**, mas continua opcional para o build isolado. (Research: SLSA/pipeline-security — "Generating attestations without enforcing them is theater" (Arbure); "verification has to be an enforced gate, not an optional check" (Encryption Consulting); C2PA `humanOversightLevel` consumido por validadores para decisões automatizadas; trailer-lint em CI como padrão fail-closed.)
- Q: As URIs em `inputs[]` do sidecar devem ser restritas a referências locais seguras? → **A (research-backed)**: **sim** — cada `inputs[].uri`, quando presente, deve satisfazer `isSafeLocalReference` (mesma regra do manifesto): sem URL absoluta/protocol-relative/`../`/esquema externo; violação → throw (fail-fast). `inputs` permanece opcional; quando presente, cada `uri` é validada além do digest `sha256`. (Research: OWASP SSRF Prevention Cheat Sheet — validar/allowlist de URLs, rejeitar traversal/absoluto; consistência com o invariante do projeto de nenhuma referência externa/insegura em metadados autorais; o build não faz fetch de `inputs`, então é hardening/consistência, não SSRF direto.)

### Resolved clarifications (Session 2026-10-17, research-backed, batch 7)

- Q: Onde a referência PNG lossless do Tier B (e os arquivos temporários da escrita atômica) devem ser gravados, dado que `assets/` só pode conter arquivos referenciados pelo manifesto? → **A (research-backed)**: num **diretório de scratch na raiz do repositório, já ignorado pelo git** (`build/`, presente em `.gitignore`), **nunca** em `assets/`, `dist/` ou `src/`; os temporários da escrita atômica ficam no **mesmo diretório** do alvo (mesmo filesystem → `rename()` atômico, sem `EXDEV`). A referência PNG do Tier B é **insumo de cálculo**, não artefato publicável. Motivo: `findUnreferencedAssets` é exercitado por `tests/unit/media-generation.test.js:194-198`, que falha `npm run test:unit` (executado **antes** de `build:images`/`build`) se qualquer arquivo não referenciado aparecer sob `assets/`; `dist/` é apagado no início de `copyPublishableFiles` (`build.mjs:652`) e construído **depois** de `build:images`; `os.tmpdir()` pode residir em outro filesystem (tmpfs) e quebrar a atomicidade (`EXDEV`). Em CI a referência pode ser exposta via `actions/upload-artifact` (somente em falha), nunca commitada. (Research: POSIX `rename()`/`EXDEV` — atomicidade só no mesmo filesystem; padrão "final path com sufixo único" para arquivos temporários; separação intermediário-vs-saída do Next.js `distDir`; `actions/upload-artifact` para debug.)

### Resolved clarifications (Session 2026-10-17, batch 8)

- Q: O que fazer quando existe um sidecar em `media-src/` cujo master correspondente não existe (sidecar órfão)? → **A (user + research-backed)**: **fail-fast** — um sidecar órfão (cujo stem/`subject.name` não corresponde a nenhum master em `media-src/frames|audio/`) é **erro** (`orphan-sidecar` throw) no gate de verificação de sidecar de `build-images.mjs` e **falha** o passo de CI que cobre `media-src/`. A integridade referencial é **bidirecional** (sidecar↔master), simétrica ao gate existente `findUnreferencedAssets === []` (que já falha em saídas órfãs em `assets/`). Evita deriva silenciosa de proveniência e um bloco `review: approve` apontando para um master inexistente. (Research: integridade referencial bidirecional "forward+reverse" — `splunk-monitoring-use-cases` sidecar ledger audit: "every ledger entry must point at a live UC … is a CI-blocking error"; princípio geral de referential integrity; invariante próprio do projeto `findUnreferencedAssets === []`.)
- Q: Quais os limites numéricos concretos de DoS do portão de sanitização SVG (o FR-002 nomeava as dimensões mas não os valores)? → **A (user + research-backed)**: caps **explícitos e mensuráveis**, afinados ao alvo de autoria 1200×800 — **tamanho de arquivo ≤ 1 MB (1 048 576 bytes)**, **contagem de elementos ≤ 10 000**, **profundidade de aninhamento ≤ 100**, **atributos por elemento ≤ 256**; violação → throw (fail-fast). Um cap só de bytes é insuficiente (billion-laughs explode a partir de <1 KB). (Research: limites do próprio librsvg `internals/src/rsvg/limits.rs` — `MAX_REFERENCED_ELEMENTS = 500 000`, `MAX_LOADED_ELEMENTS = 1 000 000`, `MAX_LOADED_ATTRIBUTES = 65 535`, `MAX_FILE_LOADING_DEPTH = 20`, `MAX_LAYER_NESTING_DEPTH = 500` (glibc; 50 no musl); OWASP java-html-sanitizer nesting limit 256; CVE-2026-29074 SVGO billion-laughs; CVE-2019-20446 librsvg nested patterns. The 256 attributes/element cap is a project-chosen measurable value, not a librsvg-derived limit.)

### Resolved clarifications (Session 2026-10-17, research-backed, batch 9)

- Q: A regra `isSafeLocalReference` deve se aplicar a atributos `href`/`xlink:href` de SVG? → **A (research-backed)**: **não** — `isSafeLocalReference` é uma regra de caminho de arquivo (manifest/sidecar) que rejeita `#`; aplicá-la a SVG rejeitaria toda referência interna `url(#…)`, que o FR-002 exige permitir. O portão SVG tem regra própria: permite **apenas referência de fragmento** (`#…`; sem scheme/autoridade/caminho/query); rejeita absolutas, protocol-relative, de caminho relativo e `data:`. (Research: SVG 1.1 §17.1.3/§17.1.4, SVG 2 §16.1.2/§16.1.7.2, DOMPurify issues #574/#233, librsvg, OWASP SSRF allow-list guidance.)
- Q: O piso de qualidade light deve lançar erro ou apenas avisar? → **A (research-backed)**: **lançar erro** (throw, nomeando o frame), como o piso standard. O piso é contrato rígido do espaço de busca do codificador; um piso "soft" significaria "bytes sempre vencem, qualidade é best-effort" — exatamente a degradação silenciosa que o piso fecha e contradição do FR-011. O warn-only correto é o do Tier B (métrica-proxy imperfeita). (Research: Fowler; Bazel analysis/execution; Google SRE degradation; Saltzer & Schroeder fail-safe defaults; ITU-T P.910/P.800.2.)
- Q: O srcset do manifesto deve listar larguras que o master não consegue preencher (1920/2560 para masters de 1200 px)? → **A (research-backed)**: **não** — o manifesto lista apenas as larguras que o master preenche de fato (320–1200 para masters de 1200 px); a escada geradora `STANDARD_WIDTHS` permanece congelada e o guard `width > intrinsicWidth` impede upscaling. Uma entrada morta no srcset é armadilha de imagem quebrada. (Research: HTML Standard §4.8.4.2.1/§4.8.4.3.5.)
- Q: Ferramentas de relatório permissivas usam qual flag? → **A**: o modo permissivo é a opção interna `validateManifestIntegrity(..., { checkFiles: false })`; **não existe flag de CLI** (`validate-manifest.mjs` não parseia flags). A referência à flag foi corrigida.
- Q: A comparação de digest exige constant-time? → **A**: **não** (correção consolidada no batch 5); o texto residual do batch 3 foi corrigido.

### Resolved clarifications (Session 2026-10-17, research-backed, batch 10)

- Q: Como estruturar os critérios de sucesso que misturam métrica objetiva e revisão humana subjetiva? → **A (user + research-backed)**: **separar em dois critérios de resultado** — **SC-007a** (fidelidade de entrega automatizada: SSIM ≥ 0,95 standard / ≥ 0,90 light; PSNR ≥ 30 dB como piso de falha catastrófica; fail-fast standard, warn-only light) e **SC-007b** (revisão humana Tier A: protocolo documentado com decisão binária `approve`/`reject` e campos obrigatórios — **não** pontuação numérica cross-session). O *mecanismo* (métricas nativas do pipeline e referência PNG lossless por largura) fica em FR-007/plan. (Research: ISO/IEC/IEEE 29148:2018 §5.2.5; IEEE 830-1998; ITU-T P.800.2; Streijl et al. 2016; ITU-T P.910.)
- Q: Os critérios de sucesso devem nomear ferramentas/comandos? → **A**: **não** — SC-001/SC-003/SC-005 reescritos em nível de resultado (sem `npm run ...`); os comandos ficam no plan.
- Q: 1200 px basta para desktops de alto DPR (≥2×)? → **A (user + research-backed)**: **sim, mantém-se 1200 px** (a justificativa de orçamento/entropia permanece) e **adiciona-se cobertura DPR>1** à matriz de testes, para detectar regressão de nitidez por upscaling no lado do navegador. (Research: HTML Standard §4.8.4.2.1/§4.8.4.3.5.)

## Functional Requirements *(mandatory)*

> **Note**: FR-IDs are stable keys assigned during clarification batches, not sequential by appearance. References by ID are unambiguous regardless of position in this document.

- **FR-001**: O projeto deve documentar um fluxo de autoria usando **todos os apps válidos** da suíte ArtCraft que produzam masters nos formatos aceitos pelo pipeline (`SVG`/`PNG`/`JPG` para frames; `WAV` para áudio) — incluindo `vectorcraft`, `photocraft` e `designcraft` — para produzir masters em `media-src/frames/` e `media-src/audio/`. Apps cuja saída é vídeo/motion (filmcraft, effectcraft) não são usados para ativos de runtime. **designcraft** é usado apenas para arte promocional em `marketing/` (fora de `media-src/` e do pipeline); nunca produz masters para `media-src/frames|audio`. **Autoria de áudio é independente da suíte**: masters WAV produzidos por qualquer DAW estável; o `soundcraft` (pre-alpha, recursos incompletos) **não** é dependência de produção neste feature e pode ser reavaliado quando estável. **Escopo**: a produção de masters de áudio é **documentada como follow-up e fica fora do escopo das tarefas deste feature**; o estado final do feature (FR-014/SC-001) são os 4 frames.
- **FR-002**: Masters autorais devem obedecer às restrições existentes: dimensão máxima de 2560 px no lado maior (teto rígido do pipeline; o limite de 1200 px para masters autorais é definido em FR-012), conformidade com o schema v1 do manifesto. Regras de referência (duas, distintas): (a) caminhos de arquivo em manifesto/sidecar devem satisfazer `isSafeLocalReference` (sem URL absoluta/protocol-relative/`../`); (b) atributos de URL em SVG seguem a regra separada do portão (fragment-only `#…`; absolutas, protocol-relative, caminho relativo e `data:` rejeitadas — ver batch 9). **`isSafeLocalReference` é uma regra de caminho de arquivo (manifest/sidecar) e NÃO se aplica a atributos de SVG**: o portão SVG tem sua própria regra de referência (ver abaixo). **Masters SVG devem passar por portão de sanitização/validação em build-time**, com **fail-fast** em violação; a rasterização sharp não é considerada sanitização suficiente. **Escopo de ameaça**: o portão protege o host de build (SSRF via referências externas; XXE/DoS via libxml2/librsvg), não apenas os navegadores; masters nunca são publicados como SVG. O conjunto de rejeição enumerado ( `<script>`, handlers `on*`, `foreignObject`, `href`/`xlink:href` externos, DOCTYPE/entidades) é o **piso mínimo**, não uma lista exaustiva: o portão deve também rejeitar vetores CSS (`url()`, `@import`, `image-set()`, `expression()`, `-moz-binding`, `behavior:` — rejeitando obrigatoriamente o elemento `<style>` e o atributo `style` por completo em masters autorais), todas as URIs `data:` em qualquer atributo com valor de URL, elementos/atributos de animação SMIL que mutem `href`/`xlink:href` (`animate`, `set`, `animateMotion`, `animateTransform`, `discard`), elementos perigosos que o DOMPurify proíbe (`iframe`, `object`, `embed`, `base`, `meta`, `link`, `form`, `template`, `noscript`, `style`, `handler`, `listener`), `xml:base`, `externalResourcesRequired`, instruções de processamento, XInclude e **todo DOCTYPE** (não apenas entidades) para hardening contra XXE/billion-laughs, além de **caps de DoS explícitos e mensuráveis** (ver constante `SVG_DOS_CAPS` em `scripts/svg-sanitize.mjs`; violação → throw). **Postura híbrida obrigatória**: lista de rejeição como piso **mais** allow-list sobre o vocabulário SVG mínimo emitido pelo vectorcraft (fail-closed; a allow-list é o controle primário, não uma recomendação); a finalização do vocabulário da allow-list é detalhe de planejamento. **Regra de referência SVG (separada de `isSafeLocalReference`)**: em atributos com valor de URL (`href`, `xlink:href`, `url(...)` em atributos de apresentação), permite-se **apenas referência de fragmento** (`#…` — sem scheme, autoridade, caminho ou query); rejeitam-se referências absolutas, protocol-relative, de caminho relativo e `data:`. Referências internas `url(#…)` devem permanecer permitidas. O portão roda **antes** de `sourceWidth()`/`encodeImage()` (`build-images.mjs:68-98`); `failOn: 'error'` do sharp (e seu limite de pixels de entrada padrão, `limitInputPixels`) permanecem como backstop. **Parser**: o gate não pode ser apenas regex — deve usar um parser XML real, ou (preservando a restrição de nenhuma dependência nova) um tokenizer fail-closed verificável; os bytes canônicos re-serializados são os rasterizados (mXSS/parser-disagreement é um risco real). **Orçamento de expansão de referências** (DoS): `<use>`/`<pattern>` são expandidos estaticamente durante o passo de sanitização, com `maxExpandedReferences` ≈ 100 000, `maxReferenceDepth` ≈ 20 e rejeição de referências circulares; caps estáticos sozinhos não limitam a expansão (CVE-2019-20446).
- **FR-011**: `build` e `build:images` devem **falhar imediatamente** (fail-fast) diante de master inválido, variante light ausente, estouro de orçamento ou referência insegura. Nenhuma flag de skip deve ser adicionada ao build. Ferramentas de relatório podem permanecer permissivas.

- **FR-012**: O canvas de autoria para frames é **1200×800 px (3:2)** — a geometria declarada no manifesto e a maior largura entregue do comic. Masters autorais cujo lado maior exceda 1200 px são **rejeitados pelo build** (fail-fast, código de erro `invalid-master-geometry`); qualquer master acima do teto rígido de 2560 px é rejeitado com código `exceeds-pipeline-ceiling` (FR-002). **Regra operacional**: todo master sob `media-src/frames/` (ou `media-src/audio/`) é tratado como autoral e submetido ao limite de 1200 px; o teto de 2560 px é o guard genérico de segurança do pipeline, aplicável a masters fora de `media-src/` (ex.: fixtures de teste em `tests/fixtures/`). A distinção não depende de heurística de sidecar. Motivos: (a) a geometria do manifesto é congelada e `validateImageAsset` já falha em caso de divergência de geometria do arquivo base; (b) o orçamento por frame não comporta arte detalhada acima de ~1200 px; (c) pixels acima da maior largura entregue não geram benefício de entrega, mas entropia real para o codificador e tempo de build. O limite de **≤2560 px** do FR-002 permanece o teto rígido do pipeline para **qualquer** master (incluindo fixtures sintéticos de teste); 1200 px aplica-se apenas a masters autorais. **Piso explícito de qualidade**: `build-images.mjs` não degrada silenciosamente — a escada de qualidade por orçamento de bytes tem piso explícito e deve **lançar erro**, nomeando o frame, quando o orçamento ainda não é atendido no piso: standard e light — ver constante `QUALITY_FLOORS` em `scripts/build-images.mjs`.
- **FR-003**: O **contrato de saída** do pipeline (`build:images`, `build`, `validate`) permanece inalterado: formatos (AVIF/WebP/JPEG para frames; AAC/Opus para áudio), larguras de srcset, nomenclatura `-light-*` e `budget.json`. (A inalteração do runtime/player/schema é coberta por FR-009.) O manifesto lista no srcset **apenas as larguras que o master consegue preencher de fato** (para masters de 1200 px: 320/640/960/1200; a escada geradora `STANDARD_WIDTHS` permanece congelada e o guard `width > intrinsicWidth` impede upscaling). Os **scripts de build mudam**: ganham os três portões de build-time do FR-013 (sanitização/validação SVG, verificação de digest do sidecar, fidelidade Tier B), sem alterar o contrato de saída.
- **FR-004**: Nenhum binário da suíte ArtCraft deve ser adicionado ao repositório, ao `package.json` ou ao CI; a autoria é local-only. `npm run ci` deve continuar executável sem a suíte instalada.
- **FR-005**: A licença adotada da suíte deve ser a opção MIT (dual MIT/Apache-2.0); nenhum trademark/nome/marca ArtCraft deve ser redistribuído no repositório.
- **FR-006**: Masters em formato SVG devem ser convertíveis pelo pipeline existente (sharp) para as variantes raster (PNG/JPEG/WebP/AVIF), conforme validado localmente.
- **FR-007**: Deve ser realizada uma avaliação visual comparativa entre todos os 4 frames autorais e os fixtures sintéticos atuais, documentando tamanho, formato e impressão qualitativa. **Portão de qualidade em dois níveis**: **Tier A** (humano) — revisão visual por stakeholder + notas lado-a-lado (tamanho, formato, impressão qualitativa) por master, registradas via trailer de commit `Reviewed-By: <name>` **e** bloco `review` no sidecar JSON em `media-src/` (campos: `reviewer`, `reviewedAt` ISO-8601 UTC, `oversight` ∈ {`human_authored`,`human_assisted`,`human_reviewed`}, `notes`, `decision` ∈ {`approve`,`reject`}, `measuredSSIM` opcional). Auto-revisão pelo mantenedor é aceitável (mantenedor único); segundo revisor encorajado mas não obrigatório. A verificação de paleta/intervalo tonal é **protocolo humano documentado, sem portão numérico** (não é verificação automatizada). **Tier B** (automatizado, CI) — fidelidade de entrega comparando cada variante gerada a uma **referência PNG lossless do master renderizada em cada largura de entrega**, via **SSIM** e **PSNR** calculados com os filtros nativos do ffmpeg (sem nova dependência). Os thresholds exatos (SSIM ≥ 0,95 standard / ≥ 0,90 light; PSNR ≥ 30 dB; fail-fast standard, warn-only light) são definidos em SC-007a e centralizados em `scripts/delivery-fidelity.mjs`. **O comportamento warn-only para variantes `-light-*` é uma exceção deliberada e documentada ao Princípio IV da constituição** (orçamento de ativos não negociável): SSIM/PSNR são métricas-proxy imperfeitas e a degradação light é intencional; as variantes standard permanecem fail-fast. **Tier D** — fixtures sintéticos não recebem portão perceptual. Tier C (SSIMULACRA 2/LPIPS) é auxílio offline do mantenedor, não portão de CI.
- **FR-008**: A versão da ferramenta ArtCraft usada em cada integração de arte deve ser registrada via **trailer de commit** (ex.: `Authored-With: vectorcraft-cli 0.12.0`), e a revisão visual Tier A via trailer `Reviewed-By: <name>` (auto-revisão aceitável para mantenedor único), com **sidecar JSON opcional em `media-src/`** (nunca em `assets/`) para proveniência mais rica. Campos no manifesto são proibidos (schema v1 congelado). Nenhum assertion/claim/manifest C2PA é introduzido. **Convenção de nome do sidecar**: **extension-swap** — caminho = caminho do master com extensão substituída por `.json` (ex.: `media-src/frames/frame-01.svg` → `media-src/frames/frame-01.json`); stem idêntico ao do master, um sidecar por master (independente de formato); dois masters com o mesmo stem em formatos diferentes no mesmo diretório são proibidos (throw `invalid-master-stem-collision`). **Schema do sidecar** (campos obrigatórios): `schemaVersion` (string), `subject: { name (basename do master), digest: { sha256: "<64-hex-minúsculo>" } }`, `provenance: { tool, toolVersion, timestamp (ISO-8601 UTC), author }`; opcional `inputs: [{ uri, digest: { sha256 } }]`; opcional `review: { reviewer (string), reviewedAt (ISO-8601 UTC), oversight ∈ {human_authored, human_assisted, human_reviewed} (vocabulário **definido pelo projeto** para masters autorais — não os valores C2PA `humanOversightLevel`, que se aplicam apenas a conteúdo gerado por IA), notes (string), decision ∈ {approve, reject}, measuredSSIM (number, opcional) }`. Validação fail-fast: JSON inválido → throw; campos obrigatórios/tipos; `sha256` = 64 hex minúsculo; timestamp ISO-8601 UTC válido; recomputar SHA-256 dos bytes do master e comparar com `subject.digest.sha256` (mismatch → throw; comparação direta — não requer constant-time: o digest é valor público de integridade, não segredo); `subject.name` deve igualar o basename do master (stale → throw); cada `inputs[].uri`, quando presente, deve satisfazer `isSafeLocalReference` (sem URL externa/absoluta/protocol-relative/`../`; violação → throw); o bloco `review`, quando presente, é validado (tipos/enum/ISO-8601); ausente é permitido; **rejeitar campos desconhecidos** (strict). No-op quando o sidecar está ausente. **Sidecar órfão** (sidecar cujo master correspondente não existe em `media-src/`) → throw (`orphan-sidecar`); a integridade referencial é **bidirecional** (sidecar↔master), simétrica ao gate existente `findUnreferencedAssets === []`. Tier A exige o bloco `review` + trailer `Reviewed-By` para qualquer commit de integração de master. Colocação: o sidecar vive ao lado do ativo que descreve, **fora da árvore publicável** — raízes permitidas: `media-src/` (masters) e `marketing/` (arte promocional); proibido em `src/`, `assets/`, `dist/`. O verificador de digest/órfão cobre **todas** as raízes permitidas (fail-closed), para que nenhum sidecar fique não verificado. Enforcement de colocação independente do nome. A divisão de enforcement (digest do sidecar em build; trailers + bloco `review` apenas no passo de CI) é detalhada em FR-013(e). **Política de versão (docs-only, sem enforcement em CI)**: nenhuma versão mínima/recomendada é imposta no CI ou no preflight (ArtCraft é local-only; impor violaria FR-004/SC-005). Documenta-se em `docs/authoring.md` uma versão **"testada-com"** (semeada do inventário validado, ex.: `vectorcraft 0.12.0`), atualizada quando uma versão mais nova for validada. Drift é tratado por **registro, não bloqueio**: o script de CI valida sintaxe e presença do trailer em commits que toquem `media-src/`, mas aceita qualquer versão mais nova; quando trailer e sidecar coexistem, devem concordar — `provenance.tool` + `provenance.toolVersion` devem ser iguais ao trailer `Authored-With` (igualdade exata de string após normalização mínima: colapsar espaços em branco e remover o `v` inicial da versão; sem case-folding, sem aliases, sem intervalos semânticos). Reprodutibilidade protege-se pelo digest do sidecar (bytes) + portão Tier B (SSIM/PSNR), não por pinagem da ferramenta de autoria (SLSA não cobre passos de autoria local; no máximo SLSA Build L1 "processo documentado"). Pinagem exata reserva-se a saídas de mídia byte-reprodutíveis apenas se necessário.
- **FR-013**: Os portões de build-time são implementados em módulos dedicados e **invocados por** `scripts/build-images.mjs`, o único módulo que enxerga simultaneamente os masters e as variantes geradas: **(a)** o portão de sanitização/validação de SVG vive em `scripts/svg-sanitize.mjs` e é **invocado por** `build-images.mjs` **antes** de `sourceWidth()`/`encodeImage()`; **(b)** a verificação de digest do sidecar vive em `scripts/sidecar.mjs` e é **invocada por** `build-images.mjs` por master, antes da codificação; **(c)** o portão de fidelidade Tier B vive em `scripts/delivery-fidelity.mjs` e é **invocado por** `build-images.mjs` **depois** de `ensureImage()` para cada variante gerada; **(d)** a escrita atômica vive em `scripts/atomic-write.mjs` e é usada por `build-images.mjs` para toda saída de variante (imagem/áudio e a referência PNG do Tier B) — arquivo temporário no mesmo diretório + `rename`, de modo que uma interrupção nunca deixa saída parcial e reexecutar o build é sempre seguro; **(e)** a verificação de trailers de commit **e do bloco `review` do Tier A** vive em `scripts/ci-trailers.mjs` e é **invocada apenas** por um novo passo em `.github/workflows/ci.yml`, **nunca** em `npm run ci` (execuções locais/offline/tarball permanecem inalteradas). **Portões adicionais**: (f) larguras de srcset do manifesto (apenas preenchíveis pelo master) e (g) ausência de binários ArtCraft (SC-005, verificação fail-closed: `git ls-files` não contém binários ArtCraft e nenhum binário ArtCraft resolve no `PATH`/no `node_modules`). `scripts/build.mjs` nunca acessa `media-src/`, portanto não pode hospedar (a) nem (b). O passo de CI **deve** usar `fetch-depth: 0` (o workflow atual faz checkout em depth 1): para cada commit que toca `media-src/`, exige um sidecar com `review` (`decision: approve`) e os trailers `Authored-With`/`Reviewed-By`; commits que **removem** um master exigem os trailers, mas não sidecar (deletion não tem sujeito), e o sidecar extension-swap correspondente deve ser removido no mesmo commit (senão `orphan-sidecar`); **renames** são tratados como delete+add (o sidecar antigo é removido e o novo carrega `subject.name` do novo basename); o intervalo de enforcement é definido por evento de CI (PR: `base..head`; push: `before..after`), sem fronteira fixa; um **sidecar órfão** (sem master correspondente) → falha. Colocação do sidecar: um sidecar é honrado **apenas** em `media-src/`; um `.json` perdido em `src/` seria publicado silenciosamente, e um em `assets/` falha o check existente `findUnreferencedAssets`. A **referência PNG do Tier B** e todos os temporários são gravados sob um **diretório de scratch na raiz já ignorado pelo git (`build/`)**, nunca em `assets/`/`dist/`/`src/`, sempre no mesmo filesystem do alvo (batch 7).
- **FR-014**: A feature deve produzir masters autorais para todos os 4 quadros do comic (frame-01…frame-04) em `media-src/frames/`, substituindo integralmente os fixtures sintéticos. O estado misto (fixtures sintéticos + masters autorais) não deve ser publicado. Cada master deve ser acompanhado de sidecar com bloco `review` (`decision: approve`) e os trailers de commit correspondentes. A verificação de paleta/intervalo tonal é parte da revisão Tier A de cada master.
- **FR-009**: O player, o schema do manifesto, os orçamentos (`budget.json`) e a matriz de testes (os 5 projetos Playwright) devem permanecer inalterados; nenhuma mudança de runtime. (O contrato de saída do pipeline é coberto por FR-003.) A cobertura **DPR>1** é adicionada como verificação adicional de entrega (sem alterar os projetos nem o runtime).
- **FR-010**: Os Non-Goals da avaliação (sem integração no CI, sem filmcraft/effectcraft no runtime, sem mudança de schema/player, sem binários no repo) devem ser respeitados. A adoção de "todos os apps válidos" aplica-se apenas à **autoria** de masters, não à integração no CI nem ao runtime.

## Success Criteria *(mandatory)*

- **SC-001**: **Todos os 4 quadros** do comic (frame-01…frame-04) autoralizados (vectorcraft/photocraft) e integrados (qualidade mensurável: ver thresholds Tier B em SC-007a) em `media-src/frames/` — **nenhum** fixture sintético permanece (o estado misto sintético+autoral **não** é publicado; o "pelo menos um" anterior era o mínimo, não o alvo); o pipeline de build completo completa com sucesso e sem violação de orçamento (sequência canônica: `npm run validate && npm run build:images && npm run build`; a verificação T030 adiciona `npm run test:unit` e `npm run report` como suplemento) (I1).
- **SC-002**: Orçamento por frame ≤ 300 000 bytes — **soma** do maior AVIF + maior WebP + maior JPEG do frame (neste feature o componente de áudio é 0, pois a autoria de áudio é follow-up; quando houver áudio, somar o maior AAC/Opus do frame), com variantes light **excluídas** do valor por frame mas **incluídas** no total — e total de ativos ≤ 30 000 000 bytes mantidos (baseline medido: 44 768 B no frame mais pesado — soma do maior AVIF + maior WebP + maior JPEG; folga ≈ 255 KB; total 1,45 MB de 28,61 MB).
- **SC-003**: Todos os portões de release (validação de ambiente, validação do manifesto, testes unitários, geração de mídias, build, e2e e perf) passam sem regressão após a integração (baseline: verde atual).
- **SC-004**: `docs/authoring.md` existe e contém, no mínimo: (1) passo-a-passo do fluxo de autoria; (2) ferramentas + versão "testada-com"; (3) rastreabilidade (trailers + sidecar); (4) licenciamento MIT; (5) arte promocional em `marketing/` (baseline: inexistente).
- **SC-005**: Nenhum binário ArtCraft no repositório/CI (verificável por inspeção dos arquivos versionados e pelo gate de ambiente).
- **SC-006**: Lighthouse perf ≥ 0,9, a11y ≥ 0,95, CLS < 0,1, LCP ≤ 2500 ms inalterados (baseline: valores pré-integração registrados em T005a via Lighthouse).
- **SC-007a** (fidelidade de entrega automatizada): cada variante **standard** gerada preserva fidelidade **≥ 0,95** (SSIM) em relação ao master na largura de entrega; variantes **light** **≥ 0,90** (degradação intencional); **PSNR ≥ 30 dB** como piso de falha catastrófica. **Fail-fast** para standard, **warn-only** para light. (Thresholds centralizados em `scripts/delivery-fidelity.mjs` — ver plan.md, seção Quality thresholds; D2.) **O warn-only para `-light-*` é uma exceção deliberada e documentada ao Princípio IV da constituição** (orçamento de ativos não negociável) — SSIM/PSNR são métricas-proxy imperfeitas e a degradação light é intencional; variantes standard permanecem fail-fast. (O mecanismo — métricas nativas do pipeline existente e referência por largura — está em FR-007/plan.)
- **SC-007b** (revisão humana Tier A): existe, por master, avaliação visual comparativa **documentada** (notas lado-a-lado: tamanho, formato, impressão qualitativa) incluindo verificação de paleta/intervalo tonal como **protocolo humano documentado, sem portão numérico** (não é verificação automatizada), com **decisão binária** (`approve`/`reject`) e campos obrigatórios registrados. É um **protocolo humano documentado** — **não** um portão automatizado e **não** uma pontuação numérica cross-session. (Tier D excluído do portão perceptual.)

## Key Entities & Data Models

> **`data-model.md` é o superconjunto autoritativo**; esta seção lista as entidades primárias (`AuthoredMaster`, `AuthoringWorkflow`, `ProvenanceSidecar`). `TierAReview`, `TierBGate`, `GeneratedVariant` e `TierBReference` são definidos em `data-model.md`.

### Entidade: AuthoredMaster
- `path`: caminho em `media-src/frames/` ou `media-src/audio/`
- `format`: `svg` | `png` | `jpg` | `wav`
- `tool`: string livre (nome do app ArtCraft ou outro produtor válido), não enum fechado — a validade é por formato/restrição (FR-001), não por allowlist de apps. Opcional (ausente quando a proveniência é desconhecida).
- `toolVersion`: string (ex.: `vectorcraft-cli 0.12.0`)
- `dimensions`: `{ width, height }` (frames) ou duração (áudio)
- `budgetCompliant`: boolean (≤ 1200 px lado maior para masters autorais; ≤ 2560 px teto rígido para qualquer master; ≤ 300 000 bytes por frame — soma dos maiores AVIF+WebP+JPEG; ≤ 30 000 000 bytes total)

### Entidade: AuthoringWorkflow
- `steps`: lista ordenada (criar no app → exportar → colocar em `media-src/` → rodar pipeline → validar)
- `traceability`: registro de versão da ferramenta por integração

### Entidade: ProvenanceSidecar (opcional, em `media-src/`, nome por extension-swap: `<master-stem>.json`)
- `schemaVersion`: string (obrigatório; valor atual `"1.0"`)
- `subject.name`: basename do master (obrigatório)
- `subject.digest.sha256`: 64 hex minúsculo do SHA-256 dos bytes do master (obrigatório)
- `provenance.tool`: string (obrigatório)
- `provenance.toolVersion`: string (obrigatório)
- `provenance.timestamp`: ISO-8601 UTC (obrigatório)
- `provenance.author`: string (obrigatório)
- `inputs`: lista opcional de `{ uri, digest: { sha256 } }` — `uri` deve ser referência local segura (`isSafeLocalReference`); URI externa/absoluta/traversal → throw (fail-fast)
- `review` (opcional): bloco de revisão visual Tier A, validado quando presente:
  - `reviewer`: string (obrigatório dentro do bloco)
  - `reviewedAt`: ISO-8601 UTC (obrigatório)
  - `oversight`: enum {`human_authored`, `human_assisted`, `human_reviewed`} (obrigatório) — vocabulário **definido pelo projeto** para masters autorais (não os valores C2PA `humanOversightLevel`, que se aplicam apenas a conteúdo gerado por IA)
  - `notes`: string (obrigatório) — observações lado-a-lado (tamanho, formato, impressão qualitativa)
  - `decision`: enum {`approve`, `reject`} (obrigatório)
  - `measuredSSIM`: number (opcional) — fidelidade Tier B medida para o master (valor SSIM; PSNR reportado separadamente quando disponível)

## Non-Goals *(fora de escopo)*

- **Integração no CI**: nenhum binário ArtCraft em runners; `npm run ci` não depende da suíte.
- **filmcraft/effectcraft no runtime**: proibido pelo Princípio II (médium definido: HTML/CSS/JS + quadros de imagem).
- **Adoção de todos os apps no runtime/CI**: apenas subconjunto justificado para runtime (vectorcraft + photocraft); "todos os apps válidos" (FR-001) aplica-se apenas à **autoria** de masters. Arte promocional (designcraft) vive em `marketing/`, fora do runtime e do pipeline (ver clarificação batch 2).
- **Mudança de schema v1 ou do player**: fora de escopo.
- **Embutir/versionar binários no repo**: proibido.
- **Option C (integração completa no pipeline)**: adiada para avaliação futura.
- **Produção de masters de áudio (WAV)**: o fluxo é documentado, mas a autoria de áudio fica fora do escopo das tarefas deste feature (follow-up).
